# Company Hierarchy MVP — Implementation Plan

## Architecture decisions for implementation

1. **Identity:** `users.id` remains the stable internal Person ID and the target of `channel_accounts.user_id`. A new tenant-scoped `people` record with the same ID holds customer employee identity, work email, role, Pulse eligibility, and organizational lifecycle. New provisioned Persons get a `users` row and a `people` row in one transaction. Existing conversation users remain legacy until explicit reconciliation. This avoids making incomplete historical rows satisfy new mandatory customer fields.
2. **Authority:** Unit and Team placement and owner Person IDs are authoritative. `teams.managerSlackUserId` remains a compatibility field for existing survey/report delivery; it never determines new hierarchy ownership. No editable manager pointer is added to Person.
   New hierarchy tables use the `org_` prefix so existing `teams` and `team_memberships` remain untouched during transition. A single `org_employee_placements` row represents either direct Unit membership or Team membership, and the Team/Unit composite key prevents contradictory placement.
3. **Mutation boundary:** TypeScript application operations validate the complete affected graph and commit through database transactions. Database keys and checks enforce local invariants; operations enforce cross-table minimum counts and legal transitions.
4. **Customer authorization:** Company Admin requires a corporate OIDC session bound to an eligible same-tenant Person with an active `company_admin` capability. A draft Person with its inactive runtime user may administer setup before Unit rollout; an inactive Person or deleted user may not. The existing `ADMIN_API_KEY` remains an explicitly identified internal-operator path and does not authenticate a customer.
5. **Migration/cutover:** Add schema without changing current queries. Inventory existing Teams, memberships, and manager Slack IDs by tenant; map only unambiguous records to draft Units/Teams/People; quarantine ambiguous records for manual resolution. Reconcile and verify counts before enabling active hierarchy reads. Add runtime guards at the cutover so draft, inactive, and non-participant Persons cannot enter conversation, Pulse, proactive, or delivery paths. New hierarchy ownership must come from active Person/Unit/Team records after these checks pass. The 2026-09-27 product decision retains previous survey/report recipients until a separate reporting launch; report delivery and historical cohorts do not switch as part of this MVP.

## Slice 1 boundaries

- New `people` records are draft by default. The migration does not activate or backfill existing users.
- `people.id` and `tenant_id` must match the referenced `users` row through a composite foreign key. Customer employee IDs and normalized work emails are tenant-unique.
- The schema enforces the fixed MVP role-to-Pulse mapping. Capability grants and active-state transitions are later typed operations.
- This slice is not a rollout: customer endpoints, Slack linking, and runtime selectors are unchanged until their matching slices are ready.
