## 3. Assembly ownership and immutable storage

Obligation progression: `observing → assembling → snapshot_ready → delivering → delivered`; typed `pending`, `blocked`, `canceled` and `reconciliation_required` are distinct durable dispositions. Delivery status is separate from final metric completion. Assembly uses a bounded lease plus monotonically fenced token; expiry permits compute recovery, but a stale owner cannot commit. No lease takeover may resend a started transport attempt.

Before snapshot persistence, invalidation discards the entire generated package. A fresh final preparation may reuse the same cutoff and current allowed rights; it cannot reuse invalid prose, shift cutoff or silently advance an intermediate frontier. Once a snapshot exists, its payload and identity are immutable. An invalid persisted snapshot cancels its unsent remainder and requires explicit recovery review; no automatic replacement, revision, recipient change or new official final. Retain receipted/unknown attempt evidence. Replacement policy is outside this implementation approval.

Persist atomically, before any send:

1. Native snapshot identity, obligation, audience/scope/kind/Index, cycle bounds, actual cutoff/frontier, language/calendar, calculation/privacy/scoring/answer/presentation/label versions.
2. Complete channel-neutral presentation and exact Slack part bytes, all ordered parts, manifest, coverage/hashes and stable byte contract. Persist serialization canonically; on reload verify the whole package and every hash/ordinal, never regenerate localization or repack retries.
3. Restricted closed current AND selected-baseline provenance, context/generation/source authorization tokens, candidate support and minimum authorized retention deadline.
4. Exact tenant, current authorized scope recipient person frozen into this snapshot, linked active user/account, Slack workspace installation, Slack user and existing/resolved private DM binding. Prove current authority for this exact TL team or Manager unit; manager of a different unit and admin-only actors fail. No first-active-workspace selection or lookup-by-untrusted-metadata.
5. Real final-completion/support bindings described below.

Snapshot data and restricted provenance stay backend-only; Slack payload/metadata contains no participant identifiers, hashes, source references or provenance. Keep the RPT-06 literal-content, privacy and no-count/no-hidden-score boundaries. Route fields are transport arguments only. No public fallback, implicit thread or target substitution. A dedicated recipient port/repository resolves the current authorized recipient for the exact frozen team/unit against current scope authority and rejects duplicate/ambiguous links. Opening owner remains audit metadata and never grants or restricts recipient authority. Once resolved/frozen, any later recipient change blocks this snapshot; no retargeting. A bounded no-message provider preflight proves `auth.test` workspace/bot identity and `conversations.info` exact private DM/channel/user against that authenticated installation; local DB workspace/channel IDs alone are not proof. Persist content-free verified binding evidence tied to the exact monotonic credential/account binding revision, without copying any secret. Add `bindingRevision` to `schema/channel-accounts.ts` and `schema/workspace-connections.ts` through forward schema/migration changes. DB BEFORE UPDATE triggers advance it only for relevant identity/link/active/credential changes, including raw SQL; ordinary displayName/profileMetadata/updatedAt hydration must not churn it. Deletion/recreation with a new ID cannot satisfy an old frozen binding. Revision zero/missing proof grants nothing; per-part row fences prove the revision and proof are unchanged before loading the same credential. Provider preflight runs outside publication locks, uses no retries and is fake-only until live calls are separately approved. DM resolution, if needed, uses this separate explicit no-message binding stage before freeze; retries may resolve only the same authenticated tenant/workspace/person. A failed or changed binding blocks snapshot creation.

DB guards reject mutation of immutable bytes, identity, route, versions, cutoff and ordered parts. Mutable disposition/attempt state is separate. Do not rely on TypeScript readonly or content hash alone as storage immutability.

## 4. Atomic snapshot/history and lock protocol

Factor RPT-06 validation into a transaction-local function. Retain existing public `validate` behavior, but snapshot commit and each publication fence call the transaction-local function and persist under the SAME locks. Read committed state after lock acquisition; never hold locks through narrative, localization, rendering or queue calls.

Global order for lifecycle transactions that need these resources:

1. Company configuration lock only when checking new initiation/first-start; never acquire it after cycle/subjects. Final already-started validation uses frozen timing. Nonlocking configuration capture comparisons remain atomic reads.
2. Sorted advisory history-inventory keys `(tenant, history scope)` for current overall/children and every selected baseline history. Completion writers and baseline validation use the same protocol, before cycle/subjects.
3. Exact current-cycle lock, then globally sorted UNION of current and selected-prior subject locks, then analytical generation/candidate rows.
4. Required current/baseline candidates, exact source/retention and route authority rows, then obligation/snapshot/part/attempt rows in deterministic order.

Discover inventories first, reacquire in order, reread and abort/reprepare on changed membership. Do not append newly discovered historical subjects after taking subjects. Normalize captured and revalidated baseline inventory to strictly prior, nonoverlapping cycles, using the same cycle-bound rules as the selector. Do not include current/future-cycle completions: atomically completing this snapshot must not invalidate its own first send. Cross-cycle completion of a qualifying prior cycle therefore cannot change the selected baseline between validation and save/send. Do not lock prior cycles after current subjects. Source-only negative writers continue subject-first and NEVER request inventory/cycle locks afterward. Their invalidation must occur before snapshot-row changes, preventing lifecycle-row/subject inversion. Any source update invalidating existing candidates still invalidates future snapshot authorization without rewriting stored report bytes.

Hierarchy paths currently update person/org rows before participant subject locks. Sender must take route/source row locks using `NOWAIT` after advisory/subject fences; contention aborts before network, releases the complete transaction and schedules a later safe attempt. Never wait for a hierarchy row while holding subjects needed by its writer. Audit direct deletes/cascades and retention cleanup too: candidate/provenance deletion and completion support cleanup need cooperating row fences, current and historical invalidation, and content-free no-resurrection markers. Test both interleavings; do not claim all existing writers already cooperate.

Within the snapshot transaction, validate full current candidate inventory, actual cutoff/initiated frontier, rights/retention, baseline selection/meaning and exact target, then insert snapshot/parts/completion atomically. A changed selected previous final forces rebuild before snapshot, cancellation after freeze; no silent direction change.

Implementation clarification (2026-10-28): pre-snapshot history-only rebase is a full rebuild under the SAME initiated intermediate identity/current candidates/frontier/configuration/locale. A new qualifying prior final can change historical selection without admitting later current-cycle inputs. Fence the old assembly token; reacquire history inventory, current cycle and the complete sorted current/new-prior subject union afresh; authorize the new prior selection and discard/rebuild the complete prose/dynamics/package. Never patch a rendered delta or append locks late. This implements the existing pre-snapshot rebuild rule; it does not authorize a new threshold observation, refreshed current input set or any post-snapshot rebase/replacement.

TL-final and Manager-child presentations can share the SAME canonical team candidate. The first valid supporting final owns the canonical FK, additional equal-context supports do not create another metric completion. A differing candidate for an already completed same-cycle/history-scope/metric conflicts explicitly; do not publish mutually inconsistent official finals or overwrite prior completion. Database constraints/guard must enforce this, not just application checks.

Replace the unconditional old completion guard only in a NEW forward migration with a real guard proving native eligible-final snapshot, tenant/cycle/canonical scope, purpose/cutoff/frontier, metric, calculation context, generation and closed provenance match. Add the FK after safe nullable-column backfill/inventory validation as required; current legitimate completion table is empty, but fail loudly on unexpected rows.

History reader traverses real guarded support, respects current authorization and retains the immediately previous completed cycle even when its metric is invalid/absent. Preserve incompatible-latest/no-older-fallback and composition caveat semantics. Deleting expired payload or erasing sources cannot resurrect an older convenient baseline. Content-free history/identity tombstones survive only under existing authorized duties; they contain no report prose, source text or individual scalar values. ## 6. Per-part publication fence and provider outcomes

This proposal explicitly extends RPT-05 design §3's no-lock-across-transport rule only for the final publication transaction. An unlocked permit leaves a rights/route change gap before SDK invocation. Approval of RPT-07 includes the narrow bounded fence below; prior frozen specs/applied SQL remain unchanged. No model, localization, queue, DM creation, rendering or multipart batch runs inside it.

For every part in ordinal order:

1. Commit a write-ahead `attempt_started` record and monotonically fenced ownership token in a SHORT transaction before any network call. Only the caller receiving a successful FRESH write-ahead INSERT/CAS receives a one-use, process-local dispatch grant. Existing attempt lookup, lease recovery, duplicated jobs or even knowledge of the same stored token NEVER recreate this grant; do not put it in queue arguments. The grant is consumed before SDK invocation and cannot be restored by DB rollback or a second method call. An unresolved abandoned attempt is unknown. Only the next unreceipted part is claimable; previous positive receipts are required. Enforce one active transport owner per logical report. Stable client request IDs aid reconciliation but are not proof of provider deduplication.
2. Open a dedicated READ COMMITTED publication transaction, acquire inventory/cycle/subject/row fences above, verify the write-ahead token, full immutable package, source/baseline authorization/expiry and exact current route. Before SDK dispatch, CAS a token into a backend dispatch-only state and require the fresh local one-use grant. This DB CAS alone is insufficient because rollback can restore its row; a duplicated holder never obtains the fresh grant and cannot invoke twice. Contending holders abort before network. Perform one dedicated Slack post, with source/route fences held, then record a verified result and commit. Successful final-part receipt marks the logical report delivered. The caller must never wrap this transaction in an automatic retry helper.
3. If validation fails before SDK dispatch, cancel/block with an explicit definitely-not-invoked record; release the transport owner safely. If the owner dies after write-ahead claim, treat its unresolved attempt as UNKNOWN even when it may have died before sending. Never infer unsent from lease expiry.

Use a dedicated Slack WebClient/transport with `retryConfig.retries=0`, rate-limit automatic retry disabled (`rejectRateLimitedCalls`), finite request timeout (10 seconds), conservative finite DB lock acquisition timeout (2 seconds) and no SDK pagination/upload/thread/send fallback. Keep locks bounded per ONE part; every next part gets a fresh transaction and revalidation. DB failures/timeouts/commit ambiguity after invocation become unknown; do not retry the network transaction. Do not let a timeout release ownership while a still-running request can be reassigned. Abort/finish old request before explicit resolution; an unprovable termination stays unknown. No PostgreSQL transaction can undo Slack acceptance or revoke in-flight data. The guarantee is serialization of rights/route mutations against attempt initiation and no automatic duplicate send, not cross-system exactly-once delivery or revocation after dispatch. The tenant retention-policy authority row is included in NOWAIT fences, so a retention-policy edit cannot race dispatch; source/expiry clocks are rechecked immediately at dispatch; expiry afterward cannot retract acceptance.

Outcome taxonomy must be conservative and tested against the actual SDK:

- `accepted`: explicit `ok=true`, exact bound channel and nonempty valid timestamp; persist receipt tied to snapshot/part/attempt and body hash. Malformed success or channel mismatch is unknown.
- `definitely_not_sent`: local validation/no SDK invocation; or documented explicit provider rejection proving no message was created. A typed allowlist is required; any unclassified SDK/provider error is unknown. Proven rate limiting can retry with bounded Retry-After scheduling; authentication/scope/channel errors block pending correction without retargeting.
- `unknown`: request timeout, disconnect, process death, DB/receipt commit failure, unverifiable response or uncertain acceptance. Freeze the ENTIRE logical report, including later parts. No automatic resend, remaining-part send or snapshot replacement.

Earlier receipted parts remain published and immutable when later parts block. Definitely unsent recoverable failures can retry only the same next part with a new durable attempt after full revalidation. Rights/route failure cancels the remainder, never edits earlier messages. Do not mark a partially delivered report fully delivered. Do not delete or automatically resend already receipted parts.

## 7. Explicit reconciliation and operational access

Provide a local operator script and application/repository operation, no public HTTP/admin-access bypass. Reconciliation is disabled by default and requires an explicitly supplied authorized operator context scoped to this tenant/report, reason, expected current attempt/token and evidence reference; ordinary jobs cannot invoke it. Tooling uses offline supplied evidence in this implementation; it must not make live Slack lookup calls without separate authorization.

Operator decisions are immutable audited events: `confirmed_delivered` with matching channel/timestamp/part evidence; `confirmed_not_sent` with definitive evidence and terminated/fenced prior owner; or `remain_unknown`. Missing proof, absent receipts or absence from a bounded Slack history search cannot select confirmed-not-sent. CAS rejects concurrent/stale resolutions. Positive evidence attaches a real receipt and permits next-part validation. Definitive no-send resolution permits retry of the SAME bytes/target only when currently authorized. Any unresolved attempt blocks the entire report. Supplied evidence is an audited explicit human decision, not a cryptographic guarantee and never an invented provider receipt. Source/target changes do not authorize replacement or retargeting. No bulk reset/delete/force-resend switch.

Persist only structured operational status, due/actual clocks, obligation/snapshot/part/attempt IDs and approved evidence references. Logs/receipts must not contain secrets, analytical text, payloads or private transcripts. Keep full failing test diagnostics in ignored task artifacts with appropriate redaction, separate from structured harness receipts.
