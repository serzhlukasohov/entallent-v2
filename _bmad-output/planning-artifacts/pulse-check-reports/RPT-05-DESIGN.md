Date: 2026-10-26; local acceptance: 2026-10-27. Status: done locally after approval, corrective regressions, both independent rechecks and the official harness. Required by [specification](../../implementation-artifacts/spec-rpt-05-allowed-inputs-and-settlement.md).

This is one outcome: an authorized, reproducible native report dataset whose final readiness cannot hide unfinished timely work. RPT-06 consumes its safe analytical inputs; RPT-07 owns product scheduling, snapshots, final completion and delivery. Preserve RPT-01–04 and pilot behavior.

## 1. Existing boundaries and gaps

- Native scopes, frozen memberships, stops, lineages, exclusions and receipt-backed analytical proof exist. See [RPT-02 design](RPT-02-DESIGN.md). Current activity, current placement and display names cannot replace the frozen membership.
- [RPT-03](RPT-03-DESIGN.md) provides permanent literal Engagement revisions, exact receipt ordering and suppression tombstones. Its 1–10 catalog remains inactive; no defaults or historical 0–10 values change.
- [RPT-04](RPT-04-DESIGN.md) freezes one cycle-wide actual first-start cutoff. `started` does not mean inputs have settled or a valid final exists. A late cutoff may exceed immutable periodEnd; collection still obeys its original bounds.
- Pilot `V2CohortReportInputRepository.load` filters active users and `isCurrent`; its selector uses periodEnd and a qualitative final gate. Do not retrofit product semantics into this pilot path. Existing closed windows, per-person prior scores and pilot snapshots are not completed native final metric history.
- API ingress currently stamps an application Date. Message/admission persistence and Redis enqueue are separate; conversation job receipts include skips/fallbacks, not proof of semantic/finalization completion. Bundle consumption purges shown text/component mappings. Neither queue emptiness nor these receipts proves settlement.

Source investigation: `runs/rpt-05/reader-source-audit.md` and `settlement-source-audit.md`. These are static findings, not executed acceptance.

## 2. Durable receipt frontier

Add a content-free `survey_report_inbound_work` ledger and per-stage/dependency records. Its identity is tenant, user, conversation and original inbound UUID. Store exact DB receipt time, instrumentation version/trust, binding disposition, stage states, dependency IDs, fenced attempt token and sanitized failure/retry codes. No utterance, displayed text, model output, score or de-identified narrative belongs in this ledger. It must survive ordinary private-message cleanup; avoid a cascading FK from the retained ledger to `messages`. Subject erasure and typed metadata retention still apply. A newly inserted ledger may verify source ownership transactionally without permanently retaining private text.

Use forward SQL triggers on **all inbound message inserts**, not just Slack's API adapter:

1. Before stamping or inserting, take tenant `FOR SHARE`, then the established subject advisory lock. Mint trusted `received_at` with one PostgreSQL `clock_timestamp()` only after both locks. Same-subject ingress commits in receipt order; different subjects can ingest concurrently. The transaction includes message, optional job admission and work ledger; no enqueue, Slack or model call while locked.
2. API/runtime helpers omit receipt clocks on new ordinary ingress. AFTER INSERT creates the corresponding trusted work record atomically. Only a DB-authored path earns its instrumentation version; caller metadata cannot upgrade it. Freeze receipt time, tenant/subject/conversation/source identity on update. Preserve existing already-stored RPT-03 clocks.
3. Explicit-clock historical/synthetic inserts retain their supplied timestamp but create `unverified_explicit_receipt`, never trusted work. Migration inventories existing inbound metadata as `legacy_unverified`/`legacy_missing_clock`; no automatic historical proof upgrade. Such potentially eligible work blocks final settlement. No new historical-import recovery path is authorized here.
4. Reject newly inserted explicit clocks that would backdate an applicable participant's receipt into an already-started native final's eligible interval. This closes a post-seal backdate hole. Ordinary roles get no session-GUC bypass. Already-applied migrations remain unchanged; earlier synthetic fixtures use their explicit historical compatibility branch and must not be labelled settled.

RPT-04 first start takes tenant `FOR NO KEY UPDATE` before its exact cycle lock, conflicting with ingress SHARE. It therefore waits for previously admitted ingress commits; ingress waiting behind first start gets a later receipt clock. Do not restamp or extend RPT-04 cutoff. HTTP/provider arrival before durable admission is not a received event in this contract. Keep transport deduplication separate. An existing inbound UUID replays only after verifying immutable owner/clock identity and returns its original work; it cannot mint a new receipt, overwrite progress or silently accept mismatched identity.

New inbound insertion is a top-level admission transaction, never nested after worker subject/working locks. Audit API, dev, generic worker save and simulation writers. Outbound persistence does not acquire this new ingress fence. A raw explicit-clock insert remains untrusted even if another field claims a production origin.

## 3. Semantic progress and deterministic recovery

The ledger covers every potentially relevant receipt for frozen participants, including admissionless dev saves and unqueued rows. While holding ingress/claim subject locks, only read existing exact native bindings; never call `PulseReportScopeRepository.findOrCreateWindow`, which takes cycle before subject. If a binding must be created, use a separate top-level transaction in cycle -> subject order with explicit immutable cycle identity, then reread; do not guess a legacy, current-wall-clock or overlapping cycle. Receipt eligibility intersects native opening, periodStart, immutable periodEnd, earliest participation stop and the strict report cutoff. Engagement keeps its existing final-14-day unlock. A missing/unverified binding is not an ordinary no-op.

Record independent capture, native verdict, semantic evidence and permanent-finalization dispositions. Valid terminals include applied permanent result, proven no-op/not-applicable, invalid literal, permission exclusion, typed expiry or intentional deletion. `pending`, retryable failure, ambiguous delivery, lost required proof, unverified legacy and manual reconciliation are operational states; none authorizes a low-participation result. Inactive chat status does not discard already timely frozen-origin confirmations.

Progress commits with the effect it certifies: capture event, verdict/turn transaction, evidence-apply/intent transaction or permanent-insight/purge transaction. A rolled-back effect cannot leave terminal progress. A finalizer `stale` result requires an authoritative reread; an extraction intent being complete cannot cover a pending confirmed finalizer. Generation failure followed by a coaching fallback does not settle unresolved reporting work. Coalescing must retain original receipt dependencies; only completion of the relevant downstream work closes them. Cycles or cross-subject dependency references are invalid.

A processed open-ended supplement without the required timely shown confirmation is nonreportable for this final; it does not replace prior confirmed state. Do not await a post-cutoff confirmation or manufacture one. Recovery of already timely confirmed work must use its original admitted receipt, not fail merely because wall-clock periodEnd has now passed. Preserve the guard against turning delayed unconfirmed text into new post-close confirmed content.

Native verdict processing needs immutable content-free shown-form mapping **before** mutable Bundle consumption/purge: prompt/bundle IDs, question/version, component ordinal/hash, working revision identity, positive delivery/ACK clocks and form hash. Bind inbound to the actual historically shown form as of its receipt; never infer from the current pending Bundle. Store applied per-component outcomes by original inbound/form identity. A short subject-locked claim orders only native verdict/working-mutation stages by `(received_at, inbound_uuid)`, not whole receipt/evidence/finalization completion. Earlier no-verdict or delegated extraction work records that native-stage disposition before a later native claim proceeds; delegation cannot swallow an unprocessed verdict against a shown form. An A-to-B coalesced evidence dependency must not force B to wait for A's entire downstream completion. The claim selects the lowest unresolved native mutation stage; commit effects with the same fenced token, releasing locks during normal private processing/AI. A later job waits rather than consuming an unseen earlier receipt. Reclaimed/expired claims cannot commit stale work.

Repeated agreement with the same already accepted form is an idempotent duplicate, not a second vote. A correction follows the ordinary new shown-and-confirmed revision flow; it cannot rewrite a permanent state from a stale form. Keep machine mapping so retained ordinary private outbound text can be interpreted by the existing processing adapter without reconstructing component identity from prose. This does not authorize report-reader access to private text, new provider calls from report preparation, or retention extension. Missing exact shown mapping/body after lawful purge yields explicit exclusion only when typed retention/deletion proves it; unexplained loss remains blocked/reconciliation. Legacy Bundle processing stays unchanged.

Keep numeric capture before generation/resume/coalescing. A late positive ACK cannot retrospectively qualify an earlier numeric answer. A sent message whose activation failed may retry activation with its receipt; an uncertain send must not be sent again automatically. Permanent-only receipt proof remains sufficient after ordinary private purge; do not pin private material for report readiness.

Use existing normal recovery paths for source work, with a distinct native receipt-ledger selector rather than the old provider-occurredAt/periodEnd/Bundle-status cutoff query. Durable admission/dispatch/evidence identities are authoritative; Redis is a delivery mechanism. Handle crash-before-enqueue, exhausted jobs, lost jobs, stale leases and manual-reconciliation states explicitly. Keep dataset prepare/read/settlement certification strictly observational: no recovery/requeue call is reachable from these use cases, even indirectly through a queue. A separately invoked native recovery lifecycle may resume a durably committed turn using its exact admission identity without regenerating, retry receipt-only completion, process an existing pending evidence intent or confirmed finalizer under the existing independently authorized provider lifecycle, or activate a positively delivered form without sending again. Failed/missing uncommitted conversation jobs, unresolved fallback semantics, and attempted sends without positive receipt require explicit reconciliation; no automatic model regeneration or resend. Paginate fairly; repeated blocked rows cannot starve later work.

## 4. Settlement certificate and read consistency

Add a native cycle settlement state keyed to the existing formation identity/cutoff, a monotonic generation, and per-scope input-set candidates. Final preparation requires a started RPT-04 context and a closed frontier: all potentially eligible pre-cutoff work has proven terminals and every required confirmed topic has either its permanent result or an authorized negative disposition. Missing work, proof or a failed processor returns typed `pending`/`blocked`; there is no timeout-to-insufficient conversion.

Seal in a short transaction. Take the exact persisted cycle lock, then all relevant subject locks in sorted UUID order, then progress/generation and analytical rows. Use READ COMMITTED reads after lock acquisition so previous holders' committed withdrawal/finalization is visible. A writer never acquires the cycle lock while holding a subject lock; source/permanent/progress writers bump generation atomically after their subject/private locks. Do not hold the generation row while waiting for subjects. Retention must cooperate with the same subject protocol, including the currently unlocked open-ended DELETE. The existing API user-data soft-erasure operation must enter a subject-locked reporting transaction before message/user deletion updates, invalidate affected candidates/retained history and record permitted terminal metadata before provenance disappears. Add DB guards for actual users soft-delete transitions and hard-delete/cascades as well, so a direct delete cannot bypass invalidation. Keep existing route authorization and erasure meaning; no new public rights surface or retention extension. Hard deletion removes participant/proof rows, so report-set membership/generation invalidation must precede the cascade and prohibit fallback to older baseline/topic state. Raw SQL deletion may encounter an ordinary deadlock/serialization retry, never bypass atomic invalidation. No lock crosses model, queue or transport calls.

After locks, reread the frozen context, trust coverage, stage dependencies, permissions, terminal watermarks, expiry and generation. Certification and closed input-set persistence share that transaction. A source completion/negative transition invalidates or advances generation atomically; a delayed valid result cannot sneak into a previously certified set unnoticed. Retry returns the existing compatible candidate or a typed invalidated/reprepare outcome, never a new cutoff. Current withdrawal/erasure/expiry can invalidate a candidate after settlement; RPT-07 must revalidate immediately before publication as well.

The reader is an internal scoped application port. It reads permanent safe analytics, immutable membership/proof and content-free progress only. It may not SELECT private messages/working summaries, traverse source links to text or call AI. Isolate privileged processing/recovery adapters from this adapter; verify with query/source-access spies and migrated fixtures. No new report-data/admin HTTP route is included. Company-admin capability and opening-owner metadata do not establish recipient authorization.

Intermediate preparation uses a DB-authored evaluation frontier and current allowed permanent rows, not a final settlement certificate. It may become numerically eligible while unrelated processing is pending; it never claims that every timely input is settled. Reject initiating a new intermediate after the final cutoff has been frozen. RPT-07 will own automatic triggering and durable one-time publication. Final readiness, insufficiency and baseline history must never be inferred from intermediate readiness.

## 5. Allowed-source selection

Validate tenant, cycle, scope, frozen membership, native window binding, lineage, approved question/version and policy/answer contract. Do not join current placements or require active user status; retain permitted pre-departure source-scope contributions and denominator membership. Exclude actually erased/deleted subjects. Full reporting denial removes future inputs and unpublished-intermediate denominator membership; partial denial excludes its entire lineage, retaining denominator. Do not equate onboarding participation with reporting consent.

For each person/topic, choose the latest **confirmed state** at the exact frontier before numeric eligibility filtering. Open-ended order is immutable `(confirmation_received_at, confirmation_message_id)`; Engagement is `(answer_received_at, inbound_receipt_id)`. Do not use processedAt, insertion order, `isCurrent`, provider occurredAt or finalization completion time. All required accepted source receipt times and required confirmation must pass native and cutoff bounds, not merely the earliest or latest source receipt.

Add content-free open-ended terminal/supersession watermarks before analytical deletion; numeric tombstones already provide the pattern. Rank watermarks as well as retained content. A chosen withdrawn/deleted/expired/unscored topic cannot resurrect an older score. An invalid/unconfirmed supplement is not a new confirmed state; a post-cutoff correction cannot hide the prior eligible revision. Same confirmation can span different lineages normally. Same-lineage duplicate receipt tuples may deduplicate only proven identical state/proof; conflicting state blocks with a typed integrity error, never an arbitrary insight-ID tie-break.

Then apply present negative permissions, retention and permanent proof. Require receipt-backed exact shown confirmation for open-ended and declared direct-explicit-answer 1–10 contract for Engagement. Legacy/unverified metadata is not upgraded. Filter live analytical expiry even before physical cleanup. Unexpected missing required proof is operational failure; a proven privacy/rights/expiry exclusion is not. No fallback to old assessments, private conversation or alternate versions.

Pass surviving raw values to RPT-01's metric/eligibility kernel without intermediate rounding. Complete numeric respondents require all three valid topics. Final qualitative selection independently permits finalized 1/2/3-topic and safe unscored insufficient-evidence records, including non-Engagement respondents. Keep fallback support metadata: direction/category is not concrete causal evidence. Use only surviving safe text; RPT-06 will enforce narrative support and disclosure.

Overall final gate is all complete allowed quantitative respondents with floor five; 5 of 100 qualifies. Manager team floor uses five subordinate employees, excluding own TL, with no 80% requirement; all-insufficient teams cannot suppress an eligible overall dataset. Intermediate overall uses the withdrawal-adjusted frozen denominator and RPT-01 threshold. Internal per-subject keys/provenance are restricted computation data, not narrative-model or recipient input. Return no counts/narrative for a future insufficient notice; RPT-06/07 own its serialized content.

## 6. Final metric candidates and history boundary

Persist distinct native metric candidates and closed provenance keyed by tenant/cycle/scope/purpose/frontier/calculation contract and generation. Include stable history key, boundary fingerprint, exact formation/cutoff, question-meaning/rubric or answer-contract compatibility signatures, privacy/calculation versions, composition fingerprint, raw aggregate and complete-contributor eligibility. Keep internal final open-ended metrics at floor five even when Team Lead payloads never show them. Do not use rounded visible payloads as history. Retain authorized content only under the existing typed analytical/report duties; audit tombstones contain neither topic text nor scalar answers.

A candidate is **not** a completed valid final. RPT-05 introduces the completed-final history port, pure compatibility selector and a dedicated completion-binding read surface. The database rejects production inserts/transitions into completion bindings until RPT-07 installs an actual native product-final snapshot identity/FK and guarded producer through a forward migration. No free-form completionEvidenceId, normal runtime setter, closed-window promotion or pilot import exists in this story. The actual production history is therefore empty until that integration; this is an explicit seam, not a claimed completed-history writer. Test the positive comparison rules with injected synthetic completed-history fixtures; actual DB acceptance proves candidates, read isolation and rejected premature completion. Do not bypass the guard and claim snapshot completion from fixture rows.

Choose the immediately previous completed-valid, nonoverlapping native cycle for the same history scope by cycle bounds, not processing/insert time. Validate that final's requested metric, floor, signatures, scope boundary and current authorized retention/provenance. Incompatible latest final, absent metric or insufficient prior metric returns Baseline established; do not skip to an older convenient compatible result. No compatible rescoring or scope mapping is implemented here. Composition change alone keeps comparison with a structured caveat; label/recipient change alone does not reset identity. Scope-boundary change requires a new baseline. Compare raw values with RPT-01, preserving nonzero direction despite rounded equality.

Rights/erasure/expiry invalidates affected retained candidates and future baseline eligibility through closed provenance. Preserve already delivered history; do not edit it, expose deleted text or silently recalculate a previous official result. An unusable prior result gives no comparable baseline. RPT-07 must bind actual completion to the exact candidate/cycle/scope/cutoff, distinguish completion from delivery, and install snapshot/rights checks before activation.
