## What Went Well

- Scope discipline held across the epic. Each story added one planned control surface without enabling user-facing MAF replies or Python writes.
- Review pressure found concrete fail-open risks: malformed metric evidence, stale diagnostics, percentage rollout without stable user identity, blank allowlist IDs, duplicate rollout rows, unsafe policy evidence IDs, and imprecise rollback wording.
- The rollout model reused existing feature flags instead of creating a parallel control store.
- The gate evidence became stricter and more privacy-safe with allowlisted reason codes and known migration case IDs.
- Documentation became executable enough to test. The runbook tests now protect operator-critical wording and scope boundaries.

## Challenges

- Privacy-safe evidence needed more than token-shape checks. Scenario IDs, migration case IDs, and validation reason codes all needed explicit allowlists or sanitizer rules.
- Fail-closed rollout behavior had subtle edge cases. Even `100%` rollout is unsafe without a stable identity, and duplicate rows can make behavior depend on database ordering.
- Documentation had to be precise enough to encode operational behavior. Ambiguous rollback wording could create unsafe operator actions.
- The repository remains noisy from the accumulated migration work. Reviews required careful diff scoping to avoid touching unrelated untracked files.
- Deployment readiness remains outside the completed Epic 6 scope. The gate and rollout controls exist, but non-local exposure still depends on deployment evidence and operational sign-off.

## Key Lessons

- A canary gate must fail closed for bad evidence, not only for bad metrics.
- Regex-stable is not privacy-safe by itself. Stable evidence needs allowlists, known IDs, and explicit rejection for unknown values.
- Staged rollout controls are part of safety, not just release convenience. Identity, precedence, duplicate-row handling, and malformed metadata all affect exposure risk.
- Rollback documentation is a runtime control. If operators can misread it, the system can still fail even when code paths are correct.
- TypeScript ownership needs to be named repeatedly at every new surface: messages, risk, memory, goals, follow-ups, survey evidence, ledgers, runtime-control flags, diagnostics, baseline evidence, and Slack sends.
