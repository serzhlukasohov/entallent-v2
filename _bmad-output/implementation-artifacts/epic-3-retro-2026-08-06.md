## Epic Review

Epic 3 established the evaluation substrate required before any Python MAF runtime can affect users. The completed slice expanded the migration baseline, made sensitive-case manual review a blocking state, added the canonical TypeScript-owned shadow diagnostics record, and added a privacy-safe readiness report that summarizes diagnostics without enabling canary routing.

## Completed Scope

- Story 3.1: Expanded migration baseline coverage across sensitive and ordinary scenarios, added independent required-case metadata, and made sensitive scenarios manual-review-required.
- Story 3.2: Added `runtime_shadow_diagnostics`, repository persistence, database constraints, redaction-before-write, and trace/runtime linkage.
- Story 3.3: Added the read-only shadow readiness report, per-case summaries, blocker reason codes, sparse metric handling, and gate-summary/manual-review integration.

## Evidence

- `packages/conversation-sim/src/scenarios/migration-baseline.ts` exposes the required baseline cases and was later backed by the shared contracts source.
- `packages/contracts/src/migration-baseline.ts` now provides shared required and sensitive migration case IDs.
- `packages/database/src/schema/runtime-shadow-diagnostics.ts` and migration `0008_runtime_shadow_diagnostics.sql` define the canonical diagnostics store.
- `apps/worker/src/conversation/shadow-diagnostics.repository.ts` owns redaction-before-write and idempotent diagnostics persistence.
- `apps/worker/src/conversation/shadow-readiness-report.service.ts` builds a read-only readiness report from redacted diagnostics and gate context.
- Story records show repeated scoped verification: targeted tests, package typecheck/build/lint, root `pnpm test`, YAML parsing, and `git diff --check`.

## What Went Well

- The epic preserved the strangler boundary. No `agent-service`, `MafAgentRuntimeClient`, FastAPI route, MAF workflow, production shadow execution, canary routing, or user-facing runtime behavior was added during Epic 3.
- Manual review became a real machine-readable state instead of advisory prose. Sensitive baseline scenarios cannot be summarized as canary-ready through automated pass rates alone.
- Redaction improved across the epic. Diagnostics and reports now prefer stable IDs, reason codes, counts, statuses, and aggregate metrics over raw model/provider/user content.
- Review loops caught meaningful rollout risks before commit completion: self-referential coverage, manual-review pass leakage, malformed JSONB payloads, missing stable case IDs, and privacy-sensitive report loading.
- The readiness report now gives product reviewers a concrete non-canary decision surface: `blocked`, `manual_review_required`, `insufficient_data`, or `ready`.

## Challenges

- Baseline case IDs appeared in more than one place before review forced a shared source. Coverage rules drift quickly when the same list is copied across simulation and reporting layers.
- JSONB diagnostics are flexible but dangerous. Missing or malformed comparison payloads can look like success unless the reporter explicitly fails closed.
- Redaction rules must distinguish stable identifiers from free-form strings. A key-name-only allowlist was not enough.
- Verification order still matters. Builds that clean upstream `dist` directories can break parallel worker checks that import those packages.
- Live simulation gates remain environment-dependent because model and LangWatch endpoints may be unavailable locally. Static and deterministic checks are reliable; live gates need explicit availability notes.

## Key Lessons

- Baseline coverage needs one canonical source. If simulation, reporting, and contracts need the same IDs, place them in a shared package and have consumers import them.
- Readiness logic must fail closed. Unknown diagnostic shape, missing gate context, unstable reason codes, and sensitive-case review gaps must never resolve to `ready`.
- Manual review is part of the rollout gate, not documentation metadata.
- Shadow diagnostics should be useful without becoming a privacy liability. Select only the columns the report needs, and never load raw result JSONB when aggregate fields are enough.
- Keep canary and user-facing behavior out of foundation epics. Epic 3 produced measurement substrate, not rollout behavior.
