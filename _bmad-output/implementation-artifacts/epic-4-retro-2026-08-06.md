## Epic Review

Epic 4 introduced `agent-service` as the Python/FastAPI foundation for the future MAF runtime while preserving the strangler boundary around the existing TypeScript worker. The completed slice added the service scaffold, liveness and readiness surfaces, runtime contract validation skeleton, scoped internal service auth primitives, runtime state primitives, and an inert deployment envelope.

The epic deliberately did not add `MafAgentRuntimeClient`, MAF workflows or tools, worker routing to Python, non-local shadow/canary execution, domain aggregate writes, or dashboard/admin UI.

## What Went Well

- Scope discipline held across the epic. Each story allowed one new surface and kept the next surfaces out of scope until their planned story.
- The TypeScript runtime remained the only user-facing runtime. No Python runtime client, worker routing, shadow execution, canary behavior, or aggregate ownership transfer was introduced.
- The canonical OpenAPI runtime contract became useful in Python early, before the real MAF workflow exists.
- Scoped internal auth was built as a primitive, not as a tool endpoint. This preserved tenant/workspace scoping and audit shape without giving Python side-effect paths.
- Runtime state work stayed detached from `/runtime/process-message`, but still proved the durability and session-key invariants required by AD-7 and AD-8.
- Story 4.5 closed AD-19 at the metadata level: start command, health/readiness, internal URL, env vars, secret ownership, Docker strategy, and Railway registration template are now inspectable.

## Challenges

- Review repeatedly found important edge cases after initial implementation. The recurring class was not broad feature drift; it was fail-closed behavior at the boundary.
- Scope regression tests had to evolve story by story. Earlier tests correctly blocked future work, but each subsequent story needed careful allowlist updates without weakening the remaining exclusions.
- Settings and environment naming created subtle risks. Python service env uses the `AGENT_SERVICE_` prefix, while TypeScript shared config must not begin consuming future worker URL settings before Epic 5.
- Security review for internal auth surfaced several non-obvious hardening gaps: guard-level audit recording, claim-less rejection audit, weak secrets, excessive token lifetimes, duplicate auth headers, and trace ID sanitization.
- Durable state review found that "works locally" was not enough. Non-local shadow requires private file permissions, absolute durable paths, no `:memory:` SQLite, blank-key rejection, standard JSON, and normalized corrupt-payload errors.
- Deployment envelope review found operational gaps that tests did not initially force: real SQLite dependency failures must become safe readiness 503 responses, and the non-root container user needs a writable runtime state path.

## Key Lessons

- Foundation stories still need adversarial review. The most valuable fixes were edge-case protections around auth, settings, state, readiness, and deployment metadata.
- Scope tests are migration infrastructure. They should move forward one intentional allowance at a time and continue blocking future epic surfaces.
- Fail-closed behavior must be tested with real dependency failure modes, not only monkeypatched domain exceptions.
- A deployable service envelope is more than a Dockerfile. It must include writable runtime paths, env/secret ownership, health semantics, registration metadata, and explicit non-deployment boundaries.
- The Python service can accumulate strong primitives without owning side effects. This is the right posture until shadow/canary data proves the MAF candidate is safe.

## Technical Debt And Deferred Work

- Docker image build was not run locally; Story 4.5 tests inspect the Dockerfile and metadata but do not require a Docker daemon.
- Railway registration is documented as an inert template only. The real `agent-service` service, volume, secrets, and health check still need operational registration before non-local shadow.
- The strict runtime-boundary request shape remains unresolved before `MafAgentRuntimeClient`.
- The runtime endpoint still returns a not-implemented stub; no MAF workflow, tools, model calls, or candidate diagnostics exist yet.
- SQLite is sufficient as the current foundation backend, but architecture still defers the final Redis/Postgres decision before production-grade non-local shadow execution.
- Existing non-blocking warnings remain: Starlette `httpx` TestClient deprecation in Python tests and pre-existing `apps/api/src/main.ts` no-console lint warnings.

## Epic 5 Preview

Epic 5 is `MAF Conversation Workflow Candidate`. It introduces the disabled TypeScript HTTP client, then adds the Python workflow skeleton, read-only context tools, structured candidate output, and shadow-mode integration.

Planned stories:

- Story 5.1: Add disabled `MafAgentRuntimeClient`.
- Story 5.2: Implement MAF workflow skeleton.
- Story 5.3: Implement read-only context tools.
- Story 5.4: Return structured MAF candidate results.
- Story 5.5: Integrate MAF candidate into shadow mode.

Dependencies from Epic 4:

- `agent-service` exists and can validate runtime requests locally.
- Scoped internal service auth primitives exist but are not wired into tool calls.
- Runtime state primitives exist but are not used by the runtime endpoint.
- `/health/live` and `/health/ready` exist with separate liveness/readiness semantics.
- Deployment metadata exists, but actual Railway service registration has not been executed.

Preparation needed before Epic 5:

- Resolve or explicitly document the strict runtime-boundary request shape before Story 5.1.
- Keep `MafAgentRuntimeClient` disabled by default and fail-closed when URL/readiness/auth configuration is absent.
- Decide whether Epic 5 uses `AGENT_SERVICE_INTERNAL_URL`, `AGENT_SERVICE_URL`, or a documented compatibility naming scheme for the worker client.
- Preserve TypeScript side-effect ownership: Python returns proposals and diagnostics only.
- Keep read-only tools tenant/workspace scoped through authenticated claims, not request JSON fields.
- Keep deterministic checks local; only add Docker/Railway verification when the story explicitly owns that operational step.
