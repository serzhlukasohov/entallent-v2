## What Went Well

- Scope sequencing worked. Each story opened one planned surface and kept later surfaces blocked through explicit guardrail tests.
- The TypeScript runtime boundary held. Even after Story 5.5, user-facing replies still come from `TypeScriptAgentRuntime`; MAF output is diagnostics-only.
- The canonical OpenAPI contract carried useful weight on both sides of the boundary. TypeScript validates outgoing requests and incoming results; Python validates requests, results, and errors.
- Review pressure caught production-relevant gaps before canary: missing default fetch, missing default timeout, raw context leaks, weak response validation, idempotency collisions, and context scoping mistakes.
- Proposal-only output gave product-reviewable MAF behavior without creating dual writers for memory, goals, follow-ups, risk, messages, or ledgers.

## Challenges

- Boundary and privacy defects appeared repeatedly once real data moved through the candidate path. Context reads, recent turns, memory content, risk evidence, and shadow diagnostics all needed stronger redaction or scoping than the initial implementation provided.
- Scope regression tests needed careful evolution. Earlier tests correctly blocked future surfaces, but each new story had to allow exactly one new capability without accidentally allowing canary, command tools, Python writes, deployment mutation, or UI.
- Cross-language request construction was subtle. The TypeScript request had to include enough canonical data for Python without fabricating message text, timestamps, session scope, or idempotency fields.
- The build graph has a practical footgun: package builds that clean `dist` can make dependent worker verification fail if run in the wrong order.
- Shadow execution currently runs inside the worker job path. The timeout bounds the risk, but Epic 6 should decide whether this remains the intended operational shape before user-facing rollout.

## Key Lessons

- Shadow mode is not just "call the second runtime." It needs canonical request construction, bounded context, idempotency, redaction, latency limits, and diagnostics durability.
- Fail-closed behavior has to cover helper failures too. Diagnostic provider, diagnostic recorder, invalid config, malformed responses, and tool failures must never block the TypeScript reply.
- Privacy bugs are easiest to introduce at summarization boundaries. Recent-turn previews, memory snippets, risk evidence, and validation payloads need allowlists rather than raw text truncation.
- Deterministic policy must shape candidate output before comparison. Proactive pauses, survey blocks, sensitive memory suppression, and unsupported goal updates need stable reason codes in contract-valid output.
- Canary readiness needs hard blockers for invalid or missing shadow diagnostics. Passing local workflow tests is not enough evidence for user-facing exposure.

## Technical Debt And Deferred Work

- `maf_canary` remains TypeScript-only by design; Epic 6 owns user-facing exposure gates.
- Non-local shadow/canary still needs operational deployment evidence for `agent-service`, including Docker image start, writable durable state path, internal URL, secrets, and readiness.
- Shadow candidate execution is awaited inside the worker job path. This is bounded by timeout, but the operational model should be confirmed before canary.
- Existing warnings remain non-blocking: Python Starlette/httpx TestClient deprecation and pre-existing `apps/worker/src/main.ts` no-console lint warning.
- Several open retro action items remain ongoing verification practices, especially sequential upstream package builds and shared baseline case ID sourcing.

## Epic 6 Preview

Epic 6 is `Canary Readiness And Rollout Gates`. It decides whether MAF is safe to expose using baseline and shadow diagnostics, staged rollout controls, safety/privacy/consent checks, and rollback rules.

Planned stories:

- Story 6.1: Add canary gate evaluation.
- Story 6.2: Add staged rollout controls.
- Story 6.3: Preserve safety, privacy, and consent in canary.
- Story 6.4: Document rollback and ownership-transfer rules.

Dependencies from Epic 5:

- Shadow diagnostics can record valid and invalid MAF candidate outcomes.
- Candidate failures and validation failures are safe and should block canary readiness.
- Candidate results include structured risk, memory, action, and diagnostics data for comparison.
- TypeScript remains side-effect owner, so Epic 6 can evaluate canary readiness without dual-writer risk.

Preparation needed for Epic 6:

- Treat invalid, missing, unsafe, or stale shadow diagnostics as canary blockers.
- Keep `maf_canary` disabled until gate evaluation, staged rollout controls, privacy/consent checks, and rollback rules are in place.
- Decide how latency/cost thresholds are evaluated from recorded shadow diagnostics.
- Keep all gate evidence privacy-safe and avoid raw Slack text, prompts, tokens, secrets, full payloads, or stack traces.
- Preserve global kill switch and denylist precedence over any staged rollout control.
