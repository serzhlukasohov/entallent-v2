## Epic Review

Epic 8 completed the fast-track validation layer needed before making Microsoft Agent Framework user-facing. The epic proved three separate confidence points:

- Story 8.1 proved the Python `agent-service` can call Microsoft Agent Framework with a real OpenAI-compatible provider and return a contract-valid candidate runtime result.
- Story 8.2 proved the TypeScript router/client shadow boundary can validate a Python candidate without network credentials and without changing the user-facing result.
- Story 8.3 proved the full local TypeScript-to-Python shadow path over HTTP can obtain a real MAF model candidate through `MafAgentRuntimeClient`.

This epic did not switch production traffic to Python. TypeScript remains the user-facing side-effect owner. Python MAF output remains candidate-only until a dedicated primary cutover story changes runtime selection deliberately.

## What Went Well

- The migration goal is now validated end to end: TypeScript can call Python, Python can execute Microsoft Agent Framework, and the result validates against the shared runtime contract.
- The live smoke command is practical for local proof because it reuses root `.env` aliases without committing canonical production env changes.
- Candidate-only semantics were preserved throughout the epic. No story enabled `maf_canary`, changed production worker routing semantics, or transferred side-effect ownership to Python.
- BMAD review found real hardening issues before primary cutover: redaction allowlists, malformed diagnostics, unsafe trace IDs, explicit disabled provider handling, child process cleanup, startup timeout, and safe failure reasons.
- The same stable evidence fields now work across Python-only smoke, deterministic TypeScript shadow validation, and live TypeScript-to-Python shadow smoke.

## Challenges

- The first live test attempt exposed an environment loading gap: credentials existed in root `.env`, but smoke tooling needed to load them explicitly.
- The fast-track path compressed several validation concerns into local tooling. That was useful, but it increases the need for a tightly scoped primary cutover story.
- The worktree is noisy from sequential migration stories. Review discipline must continue to use story-scoped file lists and diff ranges where possible.
- The original rollout design included canary ceremony, but the product context changed because there are no real users yet. The plan now needs to reflect faster primary validation without pretending the old canary path is still the next best step.

## Key Lessons

- A working MAF migration needs an end-to-end smoke command, not only unit tests or service-local validation.
- Fast-track is reasonable in the current product state, but it should become an explicit primary cutover story with named rollback behavior, not an untracked config flip.
- Evidence redaction needs to be fail-closed and field-specific. Broad "safe-looking string" checks are not enough for runtime diagnostics.
- Local smoke tooling should own local convenience behavior, such as `.env` alias inference, while production config remains explicit.
- Child process management is part of test quality when validation scripts start services on behalf of the developer.

## Technical Debt And Deferred Work

- Production/user-facing primary MAF routing is still not enabled.
- Non-local deployment readiness evidence remains open before relying on Python outside local execution.
- TypeScript remains the side-effect owner; Python still returns proposals and candidate results only.
- The accumulated migration diff should be reviewed or committed in coherent slices before broader handoff.
- Existing non-blocking warnings remain: Vite CJS deprecation in TypeScript tests and Starlette/httpx TestClient deprecation in Python tests.

## Next Epic Preparation

No Epic 9 exists in the current planning artifacts. The next migration slice should be created as a focused fast primary cutover story.

The story should:

- Add an explicit local or environment-controlled primary MAF runtime mode.
- Route selected worker processing through `MafAgentRuntimeClient` as the user-facing runtime only when the explicit control is enabled.
- Preserve TypeScript fallback before side-effect commit boundaries.
- Keep Python side effects out of scope.
- Keep `pnpm maf:shadow:smoke` as a required pre-cutover check.
- Add a local smoke or focused integration path that proves a real user-facing candidate can be produced through Python before manual app testing.

The story should not add deployment UI, dashboard/admin UI, Python-owned writes, command tools, or ownership transfer.
