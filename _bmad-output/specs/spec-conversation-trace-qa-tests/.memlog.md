- (direction) Illia 2026-10-31: QA finds bot bugs in Slack with only the chat text; hidden state (memory, goals, pulse cycle, onboarding, intent, plan, writes) is invisible, so bugs cannot be analyzed or reproduced.
- (direction) Illia: QA can write employee replies but cannot build the context, so they cannot author sim tests from scratch.
- (direction) Illia: adding the trace logger to production is approved; all conversations are test conversations for now.
- (direction) Illia: run BMad to implement; mode express (input rich).
- (decision) One precondition format for every test: state snapshot before the test; tests do not care whether it came from a log or a recorded run.
- (decision) Test = precondition file + employee replies + expected result in plain language.
- (capability) CAP-1 Precondition file: a sim test starts from a versioned precondition file holding history, memory, goals, style, user profile, onboarding state, pulse cycle state, local time.
- (capability) CAP-2 QA test as data: QA adds a test by writing a data file (precondition ref, replies, expected, story, tags); pnpm sim discovers and runs it without test code.
- (capability) CAP-3 Expected result: plain-language expectations become judge criteria; optional hard checks from a fixed menu; each shows as a row in the report actual-result table.
- (capability) CAP-4 State presets: named presets for states hard to reach by chatting (onboarding done, cycle open N of M topics, elapsed time) composable into a precondition.
- (capability) CAP-5 Record and approve (path B): QA replies run live once, the state after them becomes a candidate precondition with a report; QA approves it into a frozen file; later runs use the frozen file without setup LLM calls.
- (capability) CAP-6 Production trace: the worker records each real conversation turn with the same data as the sim trace, captured at turn time.
- (capability) CAP-7 Trace view: QA opens a conversation trace as the same report page as sims (chat, icons, per-turn details).
- (capability) CAP-8 Precondition from trace (path A): QA picks a bot reply in a traced conversation and gets a test whose precondition is the state before that turn and whose first step is the employee message that triggered it.
- (constraint) Trace state is captured at turn time, never rebuilt from current DB state (memory and cycle change afterwards).
- (constraint) Trace is diagnostic only: a trace failure never blocks, delays or alters the turn, reply, delivery or queues.
- (constraint) Privacy: trace off by default behind a per-tenant switch; text and state content encrypted with FIELD_ENCRYPTION_KEY; retention with automatic purge; tenant-scoped; admin-key access; reads and exports audited.
- (constraint) conversation_turn_effects deliberately holds no text or meaning; the trace gets its own storage instead of widening that table.
- (constraint) Precondition from trace is allowed only for tenants marked as test tenants; real employee data never lands in repo fixtures.
- (constraint) Sim and production share one trace event model so one renderer serves both.
- (constraint) Hexagonal: trace recording is wired at the composition root (decorators/ports); application use cases do not depend on trace storage.
- (constraint) TypeScript-only runtime; no MAF or agent-service.
- (constraint) Precondition files carry schemaVersion; harness rejects unknown versions instead of guessing.
- (constraint) A candidate precondition is never used by tests until explicitly approved.
- (constraint) Framework tests run without LLM calls; live runs (recording, sims) only on explicit request.
- (constraint) Schema changes go through a new forward drizzle migration.
