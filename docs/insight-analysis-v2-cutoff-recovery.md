# V2 cutoff: deferred cleanup recovery

The five-minute question cutoff scan leaves a closed Bundle restricted while a timely, persisted inbound reply has no durable conversation-job receipt. After the window has been closed for 15 minutes, the worker logs `Question cutoff deferred: overdue_reply_count=N reason=conversation_processing_pending` if any such replies remain. The count is aggregate; the log contains no message text, employee identifier, or Bundle content. A nonzero count can also reflect queue delay, so check the conversation queue before retrying.

For new Slack ingestion, migration `0036` commits a content-free conversation admission with the inbound message. If its first Redis enqueue failed and the message was persisted before cutoff, the next cutoff scan retries that admission using the same message-derived BullMQ job ID. The worker marks the admission queued only after Redis accepts it; the conversation receipt remains the condition for private-content cleanup.

If orchestration committed a scoped turn but the receipt or Redis job was lost, the cutoff scan uses the PostgreSQL admission and turn effect to queue a new conversation recovery job. That job resumes committed intents and writes the receipt without rerunning model interpretation or applying the verdict again. A committed turn remains eligible for this scan after the resolved Bundle's display text was purged. The scan also requeues a message send only if its durable send intent has no recorded send attempt. A recorded attempt with uncertain channel outcome requires manual delivery reconciliation rather than an automatic resend.

For an uncommitted failed, missing, or scope-mismatched original job, the scan logs `Question cutoff requires manual conversation reconciliation: count=N`. This aggregate signal contains no message text or employee ID; investigate it with the queue and persisted state before retrying. Older inbound messages without an admission still need manual review.

1. Inspect `GET /api/v1/admin/queues` and the `conversation` counts for `waiting`, `active`, `delayed`, and `failed`. The admin route requires the configured API key. Do not copy queue job payloads or message text into incident notes.
2. Inspect `GET /api/v1/admin/queues/dead-letter` for failed `conversation` jobs. It lists only the first page of failed jobs per queue and returns job IDs without payloads. Do not call the retry endpoint solely because the receipt is missing. Check whether the exact scoped inbound has a committed turn effect and send attempt before taking manual action. If those effects cannot be established, keep the Bundle held and escalate the case.
3. Watch the next cutoff scan. Successful conversation processing records the receipt and immediately attempts cleanup; the recurring scan retries cleanup if that attempt failed. Confirm that the aggregate overdue count falls to zero and the conversation failure count has been addressed.
4. If the count persists but no relevant failed job is available, investigate older messages without an admission, missing committed effects, or retained-job eviction using restricted operational access. Failed jobs are retained up to 5,000 per queue, while this admin list requests only indices 0–50. Do not purge the Bundle or synthesize a receipt to clear the alert: either action could discard a timely employee reply. Replay is permitted only after the prior verdict, outbound, delivery, and follow-on effects have been reconciled.

This signal and procedure are local implementation evidence. A deployed alert threshold and incident ownership still need operational acceptance.
